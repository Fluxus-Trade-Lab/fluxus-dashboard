# incident-report — 一起事故一个文件

落 `data/reference/incidents/YYYY-MM-DD_<形状的一句话>.md`（文件名用英文小写下划线，写清**形状**不是标题党：`the_green_run_did_not_run_them`、`vendor_dropped_a_completed_session`）。

**写给谁**：写给半年后遇到同一形状的那个会话。所以每一节都要能被他拿来判「我这次是不是同一件事」。

## 固定结构

```markdown
# <标题：一句话说清形状>

**日期**：YYYY-MM-DD（<哪条线>）
**形状**：<一句话，抽象到能复用的程度>
**同族**：<相关 pitfall / incident 的文件名，写清它们共有的那句话>

---

## 一、时间线
## 二、根因
## 三、影响
## 四、修法
## 五、机制升级
## 六、教训
```

## 每一节怎么写

**一、时间线** —— 谁在什么时刻做了什么、哪个闸什么时候该响没响。**时刻用绝对时间**（带时区），不用「后来」「隔天」。二分出来的转红点写「二分，不是推断」并附命令与输出。

**二、根因** —— 根因不是症状。写到「哪个量没有分辨率 / 哪个东西不在哪个闸的眼里」那一层为止：`一个 bool 没有分辨率`、`闸装在数量维，源头沿成分维被换掉`。如果只能写到「某人忘了」，那说明还没挖到根因。

**三、影响** —— **量出来的，不是形容词**。爆炸半径要分清「已确认受影响」和「模式命中」，两者分开写，各给数。每个数现场量过并写清怎么量的（命令 / file:line）。

**四、修法** —— 已经做了什么（带 commit sha）· 还欠什么（欠条要写清欠的是谁的白名单路径、谁能合）。修法里**加的那条测试必须能红**：写清它在修之前是红的。

**五、机制升级** —— 这次的教训升级成了什么可执行的东西：宪法条 / 任务书补丁 / CI 闸 / skill 的一条 gotcha。**同形状第 3 次就必须升级为机制**（三次律），写明这是第几次。

**六、教训** —— 可复用的判据，一条一句。写成下一个人能拿来自问的疑问句更好。

## 纪律

- **对抗性复核推翻自己的，要留在文里**（单开一节「⚠️ 独立验证推翻了我自己的 N 条」），不要偷偷改掉第一版——被推翻的那版本身就是证据。
- **别复制别的事故档的内容**：同族只写文件名和那句共有的话。
- 数据敏感：仓库是 PUBLIC，事故档里不写会员名、股数、美元金额、凭据。
- 落盘路径在 alex 与 ops 两条线的直合白名单内（`data/reference/incidents/`），写完直推 main，别挂在分支上。
