# data-anomaly — 查一个数据异常到成因，再修

已 `done` 4 次的活（T-1001-04 ANDG rs_rating 与 next_earnings 全空；T-1003-77 回补普通股新高新低历史；
T-1004-21 shortlist 中英字段；以及同形的几次抽查）。每次都在同一批坑上摔一次：
照报案人的读法直接改、没回到 `origin/main` 复现、把供应商失败当代码 bug 修、或者用「结转」掩盖空值。
这条把这几次的答案钉死。

## 什么时候用

报案人给的是**一个现象**（某字段空、两值打架、某票数字不对、前后两天对不上），不是一个已经想好的改法。
如果报案人已经给出了「把 X 改成 Y」的具体改法，先用 `data-contract` 判它是不是口径/字段变更，再回来走这里的第 1–2 步。

## 五步

1. **不信报案人的读数，先在 origin/main 上复现。**
   报案人的截图、事实卡、缓存 JSON 都可能是旧的。`git show origin/main:<路径>` 打出来，
   再数一遍（CLAUDE.md「说 X 不在 main 上之前先 `git show origin/main:` 打出来」）。
   复现不出来＝写「复现不出，已查 sha xxx」，不要硬修。
   多个样本一起看：「全是空」和「空了 4 只」不是同一个问题，先数清楚分母（全 universe？还是抽样？）。

2. **把异常拆成独立的几件，逐件给成因，证据是 `文件:行号` + 字段名。**
   每件只问一个问题：这个值是**谁写的、在哪一行、被什么条件分支落到的**。
   常见四类，先判再修：
   - **代码 bug**：有明确的错误逻辑。例：T-1001-04 里 `score_against_tradeable(..., na='top')` 把 NaN 排到 rank 1，
     `_rs_raw` 加权和对缺失值不跳过——这是代码。
   - **供应商失败**：上游 API 在某一晚失败，代码吞掉了异常（如 `hide_exceptions=True`）。
     例：T-1001-04 里 yfinance `calendarEvents` 连续两晚失败，`next_earnings` 变空。
     这不是代码 bug，修法也不是改解析逻辑；要看失败是不是可以隔班自己恢复，见第 3 步。
   - **口径问题**：两个字段各自正确，但定义不同，凑在一起显得打架。例：`rs_rating`（全池排名）和 `group_pctile`（组内分位）
     是两套口径（T-1001-04 结论：不矛盾，写进契约）。这类**不改代码**，改的是说明与契约行。
   - **数据本身正确**：读数是对的，报案人读错了字段或时间点。这类直接回报，写清读对的口径，不改数据。
   判不清的，宁可写「查到 A 和 B 两种可能，区分它们需要的证据是 C」，也不要选一个。

3. **修法按类型走，不通用。**
   - 代码 bug → 最小改动，加一个**离线**红→绿测试（用现成夹具如 `fake_yf_download`，别打真网络；
     T-1001-04 的 Q1 被打回过，就是测试里漏掉了原有的 assert）。
   - 供应商失败 → 不伪造数据。能结转的只结转**未过期**的日期（T-1001-04 `_next_earnings_carry` 的做法）；
     结转之后要在输出里看得出是结转的，或在 §七 写明覆盖率。别把空值改成一个看起来正常的假值。
     修完还要说清：哪几天没有、什么时候会自己恢复。
   - 口径问题 → 不动代码，在 `data/reference/DATA_CONTRACTS.md` §七 写一行（谁、何时、两个字段各自的定义、为什么不是 bug）。
   - 修法若改了字段（新增、改名、停发）→ 转 `data-contract` 的五步，包括 `schema_snapshot --check`。

4. **对外的回报和留痕，各写一处，不写两遍。**
   - 任务 `result` / `done` 的说明：每件的成因 + 证据行 + 修法 sha（或「不修，原因」）。
   - `DATA_CONTRACTS.md` §七：只在**产生了新事实**时写一行（口径、供应商故障、新结转规则）。
     §七是档案，不是派活渠道；要别线动手，必须开任务板单，不靠 §七 那一行。
   - 若异常已经影响过线上页面或研究结论，用 `incident-report` 立事故档；别在任务说明里只写一句带过。
   - 报案人若在等结论，用 `taskboard.py handoff` 或在原单 `done` 时写明，任务板会自动挂回程单，不需要另外发消息。

5. **过 gate，收尾。**
   gate 命令现场跑（`taskboard.py gate <id> --worktree <树>`），别信任务文件里的静态 gate 值。
   代码改动 gate 常为 reviewer，走 `branch-review`；纯口径说明与契约行 gate 通常为 none。
   收工前核一次：这次修的东西，报案人**下一次打开页面**时会看到什么？如果答不上，就还没收工。

## 不做的事

- 不因为「数据看起来怪」就重跑管线覆盖 `data/output/`。先查 `data/history/` 与 `archive` 里的前后值，确认是哪一班写的。
- 不在 Dashboard 死线（JST 08:30）前动结构性改动，除非异常本身就是死线故障（见 CLAUDE.md 09-17）。
- 不为了让报案人闭嘴而删字段、删行或把空值改成 0。
- 不替报案人决定业务口径。口径有争议时，问题写成一句话＋两个选项，交 `needs-andy`，不出问卷。

## 收工三问（宪法）

①这轮做成的方法：分清「代码 / 供应商 / 口径 / 本来正确」四类，是本 skill 的价值，能否固化进 methods.md 由守护进程收。
②哪条规矩碍事：若第 1 步「先 `git show origin/main`」的规矩让你慢了，记下来，不要绕过。
③下轮第一件事：写进 done 的说明，比如「T-xxxx 结转规则到期后复查」。
