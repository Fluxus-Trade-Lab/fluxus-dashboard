# content-edit — mia 执行 Andy 对外文案裁决的标准动作

已 `done` 3 次的活（T-0922-79 退款+免费栏改写、T-0928-16 梗句库续写、T-1002-86 署名角标），每次做法都重新想一遍。这条把共同步骤钉死。

这类任务的共同形状：**Andy 说过一句话（或回了一个字），文案要照着那句话改，改的是仓库里几个具体文件**——不是从零写一篇新稿。

## 第 0 步：任务文件 `andy:` 字段先查

非空＝Andy 已经裁决过，按裁决执行，**不要**再 `needs-andy` 问一遍同一件事（`T-0922-79` 的 `andy:` 字段原话「可以用」就是这种裁决，直接照办）。
空＝这个具体问题他还没表态，才真正走 `needs-andy`（见第 5 步）。

## 第 1 步：定位，不要信任务书的行号

任务描述里给的文件路径/行号可能已经漂移（内容被别的 commit 动过）。先 `grep` 任务里引用的原文字符串，核对它现在确实在那个文件、那一行，再动手。

## 第 2 步：边界检查（ROLE.md）

只改落在边界内的文件：`Fluxus_Substack/`、`Fluxus_Brand/{voice,templates,copybook,record}/`、`Fluxus_Brand/site/` 的文案。
⚠️ `Voice_Bible` / `Own_Lines` / `Ammo` 是 Andy 亲笔或亲批，本线不擅改；`Fluxus_Brand/voice/raw/` 只许追加代录他的原话，不改写已有行。

## 第 3 步：只改验收点名的那几处，范围外的发现写一句不代改

扫描时常会碰到同形状但验收没点名的实例（T-1002-86 碰到 MRNA 文章 builder 里另一处同样的署名 byline）。**不要顺手代改**——在验收清单补一行「改 / 不改 + 理由」，拿不准归谁管就开单转给对应 owner 或走 `needs-andy`，别自己把面积扩大。

## 第 4 步：裁决原文要逐字核对，不要凭记忆转述

任务里给了 Andy 的引用原句（比如结账页那句英文）当改写目标时，改完要逐字核对改写结果与批准原文一致（`diff`/`od -c` 任一都行），不是读起来差不多就算。

## 第 5 步：验收清单是回答清单，不是打勾清单

每条 `- [x]` 后面带一句「改 / 不改 + 为什么」，供复核员核验（样板见 T-1002-86：三处落款逐一答「改——落款是信末署名位置，不是正文把 Fluxus 当名字说的句子」）。只打勾不给理由，复核员没有抓手判。

## 第 6 步：推分支前先核 type（gate=reviewer 最常见的坑）

branch-review 的 Q4（「这一问是唯一的活」那条豁免）只认 `type` ∈ `content` / `deliver_pdf` / `visual` / `experiment` / `research` 这几个值——Q2 的治理文档豁免按路径判,跟 type 无关,别混。task.type 填错（比如写成 `followup`）即便内容完全一样也会稳定 FAIL（T-0928-16 的教训，T-0928-29 改对 type 才过）。推分支前先确认任务文件 `type: content`，不对就先开单改 type，别等复核判死了才查。

## 第 7 步：duplicate 不能只看 claimed 就放行

如果怀疑另一份稿子也在改同一处，别只看任务板状态——**派复核员比一比两份内容**：常见情况是一份吃到了更晚一轮 Andy 裁决（比如改了措辞），另一份没有，单看 claimed/done 状态看不出差别，内容比对才看得出该采纳哪一份。

## 第 8 步：定版前顺手核对下游真实落地物

文案改完只合进 main，不代表线上已经是新版本（T-0920-59 的教训）。如果这篇稿子有对应的 Whop 结账页 / Substack 后台贴文 / 线上页面，顺手 grep 一下那边现在显示的是不是新版本——只改了仓库草稿、线上还停在旧版本，等于没改完。

## 第 9 步：回填

`result` 字段写回合入 main 的 sha。按 `_worker_protocol.md` 第 5–6 步推分支算 gate（交互会话按 `task-protocol` 的流程）。给 Andy 的中文说明按 `fable-voice` 的车间主任腔写，不要翻译腔。

## 验收

- [ ] `andy:` 字段检查过，没有对已裁决问题重新发问
- [ ] 改动的每个文件都核过实际行号，不是信任务书写的行号
- [ ] 改动全部落在 ROLE.md 文件边界内，没有擅改 Voice_Bible/Own_Lines/Ammo，没有改写 voice/raw/ 已有行
- [ ] 范围外同形状实例（如有）已在验收清单写明「改/不改+理由」，没有代改
- [ ] 有裁决原句的，已逐字核对改写结果与原句一致
- [ ] 验收清单每条都带理由，不是只打勾
- [ ] gate=reviewer 时任务 `type` 已确认是 `content`（或其他 Q2 豁免值）
- [ ] 怀疑重复劳动时已派复核员比对内容，不是只看 claimed 状态
- [ ] 定版类任务已核对过下游真实落地物（如适用）

## 出处

正文步骤取自三次真实执行：T-0922-79（退款条款+L1-L5免费改写，裁决留痕+逐字核对）、T-0928-16（梗句库续写，type 填错导致复核 FAIL 的教训）、T-1002-86（署名角标，范围外实例「不代改」的样板）。迁完后 `agents/mia/config.json` 的 `skills_by_type` 挂上 `content -> content-edit`，不再在任务 body 里重复这套流程（T-1003-49）。
