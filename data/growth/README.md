# data/growth/ — 增长台账（增长官唯一写入方）

漏斗仪表盘的数据层。口径先于数字：**每个数必须知道从哪来、哪天量的**；量不到写空，不估。

- `metrics.csv` — 每周一行的漏斗读数（增长官周一自动追加；抓不到的列留空并在周报标「未测量」）
- `members.csv` — 会员台账（一人一行：来源/入会日/套餐/计费周期/状态/交付方式）。**当前为空 = 尚未摸底**；首次填充靠 Andy 从 Whop/Discord 后台导出或口述，任何会话代录。
- `weekly/` — 增长官每周一的增长小结（老板早报周一引用）

转化率口径（分母写死，别换）：
- 流量→引流：X profile 点击 or Substack 订阅增量 ÷ 当周展示（views）
- 引流→落地：新会员数 ÷ Substack 订阅数（阶段三启用）

## ⚠️ PII 政策（08-24 定，本仓库是 public）
会员**姓名/邮箱/单人消费明细一律不入库**——本仓库公开。members.csv 只允许聚合或匿名 id；全量名单看 Whop 后台（增长官被召唤时现场读），不落盘。

## 名单导出 SOP（08-24 起）
- **来源**：Whop 后台 Customers → Export → All time → CSV 落 `~/Downloads/exprt_*.csv`
- **归位**：改名 `whop_users_YYYY-MM-DD.csv` 移入 `data/growth/private/`（已 gitignore，永不入库）
- **频率**：召唤增长官时更新（人在场才操作后台）；周记账任务只抄聚合数
- **CSV 亮点**：29 列，含 Discord username/ID 映射（会员↔Discord 对账硬键）、churned/renewal/canceling 日期（流失预警数据源）

## 主键：person_id（2026-08-25 改制，Andy 批准）

**旧口径以「付款邮箱」为主键，已废弃。** 08-25 的审计里，同一个人被记成两行的情况出现了 **4 次**——一个邮箱买课、另一个买终身；一个走 Whop、另一个走 PayPal。结果一行显示「付了钱没进群」、另一行显示「进了群没付钱」，**两边都像异常，合起来才是真相**，并据此错误地把「交付缺口」定为当周第一优先级。

### 新结构

- **`person_id`** = 唯一主键，由本台账自己分配（`G001`…），**只递增、不重排、合并后号码作废不复用**。它不是 Discord 的、也不是任何支付平台的 id——外部 id 都会变（08-25 实例：某会员的 Discord 显示名与 handle 不同，手工 log 里记的是第三个称呼）。
- **邮箱是多值属性**，不是主键。字段 `email_count` 记录该人有几个已知邮箱（公开侧只放数量，不放邮箱）。
- **`channels`** 多值：`whop` / `paypal` / `alipay`。一个人可以同时在多个渠道付款。
- **`aliases`** 记录并入本人的旧 `person_id`，历史文档里的引用不会失效。
- 全量明细（姓名/邮箱/Discord ID/单人金额）在 `private/persons_2026-08-25.csv`，**永不入库**。

### 公开侧不放什么

姓名 · 邮箱 · Discord handle 与显示名 · **单人消费金额**（`gross_known_usd` 只存 `private/`）。`price_usd` 例外——那是**档位标价**不是个人消费额。

### 新增一人时

先按邮箱、Discord handle/ID、姓名在 `private/persons_*.csv` 里查一遍是否已存在——**默认假设「这可能是已有的人换了个邮箱」**，而不是默认新人。08-25 的四次合并全是这个形状。
