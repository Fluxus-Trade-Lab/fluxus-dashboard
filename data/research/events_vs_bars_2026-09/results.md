## 一句话

`ticker_events` 的 change_pct 来自 **Finviz**；本地 K 线库 `ohlc_2y` 来自 **yfinance**。两家各取各的数，
恒等式 `change_pct = close/前收 − 1` 在 110 个可判日里有 **108 天 ≥0.95**（中位 1.000）。
不成立的两天里，**2026-08-07 以前没有任何闸报过**：72 个可比读数 **0 个**配当日 K 线、**72/72 配 08-06 的**。

## 一、分辨率（先量，再信它的阴性）

| | 值 |
|---|---|
| 可判日（可比读数 ≥15） | 110 / 116 |
| 其中 ≥0.95 | 108 |
| 最差的干净日 | 2026-05-04 = **0.956** |
| 坏日 | 08-07 = **0.014** · 08-17 = **0.328** |
| 非配对日的噪声底（随便拿一天来配也能对上的比例） | 0.10–0.14 |
| 判定线 | **0.90**，放在 0.328 和 0.956 之间的空档里 |
| 具名「这一帧来自 X 日」的门槛 | **0.70**，是噪声底的 5 倍 |

真阳性对照：把真归档最近一场的 change_pct 换成前一场的，闸报红
（`test_injecting_a_replay_into_the_real_archive_turns_it_red`）。**这是在今天的真数据上量的，不是合成数据。**

## 二、08-07：三个证人，外加机制

| 证人 | 读数 |
|---|---|
| change_pct × 当日 K 线 | 1/72 |
| change_pct × **08-06** K 线 | **72/72** |
| volume × 当日 / × 08-06（独立字段，基线本来就噪，干净日 74%） | 2/77 / **77/77** |
| 逐行：72 行里有多少只配得上 08-06 | 72（0 行配不上任何一天） |

对照：干净日 09-09 是 204/204 配自己。

**机制（代码、commit、数据三方对上）**：
1. 08-07 的行有两个来源。`7596afce`（08-07 18:13 ET，收盘后）写了 317 行，全是
   `healthy_charts / momentum_97 / ema21_watch / vcp` 四个筛子的，这四个全史 change_pct 都写 0.0，
   所以这 317 行查不了也坏不了。gainers 那一族那周因为 Finviz 改名（`e8ac440e`）是零行。
2. 带值的 287 行是 `preset:*`，由 `e2554467`（08-19）的预设回填 `backfill_preset_hits.py` 写进去的。
   它用 `git log --date=short -- data/output/universe.json` 给每个快照定日期，
   **取的是 commit 自带时区（UTC）的日历日**。
3. 那几天动过 `universe.json`、且 UTC 日期是 2026-08-07 的 commit **只有一个**：`69754ed3`，
   提交于 2026-08-07 01:08 UTC ＝ **08-06 21:08 ET**，里面装的是 08-06 那场的 universe。
   `7596afce` 没动 `universe.json`。
4. 于是 08-06 的 universe 被写上 2026-08-07 的日期章。和 [[pitfall_the_exemption_makes_the_check_green]]
   是同一类错：`--date=` 读的是 commit 自己的时区，不是交易日历。

**这一处有多大**：把 `snapshot_dates` 改成按 ET 已收盘场次挑，挑中的快照会变的日期有 **36 个**，
但只量 preset 行时，102 个可判日里只有 **08-07** 真偏了帧（08-17 另有原因，见下）。
所以这个 bug 一直都在，**只在 08-07 那一次真的写坏了数据**。其余 35 天换过去的是同一场的另一个 commit。

## 三、08-17：给已有声明补一条反证

`audit_event_agreement` 给 08-17 的声明是「604 行 preset 带着 08-14 的读数」（证据是 7/7 只票内部逐位吻合）。
拿厂商 K 线量，**这些 preset 行配不上任何一天**：±25 个交易日里最高 0.202（噪声底 0.10–0.14），
08-14 只有 0.069；逐行看，99 行里有 14 行一天都配不上，剩下的分散在 20 多个日期上。
我也试了「某个起点到某个终点的累计涨跌幅」，最高 14/99。**这一步搜了约 60 种组合，这个高度正好是噪声该有的样子，不算发现。**

→ **撤下该日 preset 行这个动作不变。变的是写在旁边的机制**：「整日带着 08-14 的读数」在我能测的 99 只票上找不到外部证据。

## 四、它看不见的（明写）

1. **覆盖 13%**：K 线库 221 只 / 归档 5,067 只。只坏库外那些票的损坏，这把尺子看不见。
2. **change_pct 恒为 0 的四个筛子**全部跳过。于是 03-12、03-13、08-11~08-14 共 6 天判「查不了」，不判绿。
3. K 线是复权价，除息日会差一个股息率量级，被 0.005 的容差吃掉，同量级的真错也一起被吃掉。
4. K 线库本身是某一晚的快照，**两边同时错时会静默**。

## 五、顺手核的：commit 时钟不能拿来做闸

「market data D」这类 commit 里，提交时刻早于 D 收盘的有 **23 个**。数据层面真偏了帧的只有 **1 天**。
拿 commit 时钟做闸，每报 23 次只有 1 次是真的。**要看数据本身，不看 commit 标签。**
