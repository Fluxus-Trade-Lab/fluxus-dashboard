## 二、57% 是什么形状：43 个存活点里 19 个在同一张表上

`audit_archives.py` 顶上那张 `ARCHIVES` 注册表，**每一行的两个布尔值决定这份归档被哪几道检查看着**：

```python
"ticker_events.csv": {"date": "date", "key": [...], "counts": True,  "nightly": True},
#                                                    ↑ I4 家数塌了会不会说话   ↑ I5 时钟会不会被读
```

把 `ticker_events.csv` 的 `nightly` 从 `True` 翻成 `False`，**I5 就不再问「写这份归档的人是不是死了」**——
而那是 I5 存在的**唯一理由**（08-18，delayed_ep 在一次限流下归档了 0 行，
第二天早上能说出这件事的只有 I5）。

**19 个存活点就长在这十一行上**：除了 `leaders_log.csv`（上面的老 fixture 恰好压着它），
每一个 `counts` / `nightly` 都可以被翻转而全库 3,596 条测试一声不吭。

其余 24 个：I4 的回看窗口（5）· `--repair` 写回的列（1）· `keep_default_na`（1）·
I6a 的缺省值（2）· `main()` 的退出码（1）· 四处报告初值（8）· I7 消息截断（3）· 等价与化妆（3）。

## 三、我第一版把这 19 个全放过了，而且是明知故犯的那个形状

第一版写的是一对参数化测试，**逐个归档问行为**（造一份该塌的归档，看 I4 该不该响）：

```python
w = I4_warnings_for(name)
assert bool(w) is bool(spec["counts"])        # ← spec 取自被变异的那本字典
```

我甚至在它上面写了一段注释，说明**不要**写成 `assert spec["nightly"] is True`
那种「读自己那个常量」的测试（这条已经在本套件里被抓到三次：
09-23 的 `f'{0.2692*100:.0f}'`、09-24 的 `dirty == 1`、09-24 主动没写的 `assert HIGH == 3.0`）。

**然后我把同一个缺陷换了件衣服写了出来。** 变异体把 `counts` 翻成 `False`，
`spec["counts"]` 也跟着变成 `False`，期望值和行为一起移动——对真代码绿，对变异体也绿。
重跑尺子：**0:50 这一段 25 个存活点只死了 3 个**，注册表那 19 个一个没动。

> **判据比原则好用**：不是「别读常量」，是——
> **把这条断言的期望值那一侧遮住，它还说得出话吗？** 说不出，它就在自问自答。
> 参数化的 `parametrize` 让它看起来像在遍历十一个事实，实际是在遍历十一次同意。

修法：**期望值写死在测试文件里**，成为一张带日期的对照表（`WATCHED_ON_2026_09_25`），
十一行逐个签名 `(counts, nightly)`，再加一条防腐断言（新注册的归档必须进表）。
代价是改一个 flag 就得改这张表——**那个代价就是它的用处**：
关掉一份归档的某道检查是一个**决定**（09-18 事故的形状正是「一道检查悄悄不再适用，没人记一笔」），
这张表就是签字的地方。

改完重跑：**0:50 段 49/50（98%）**。

## 四、前后对照（同一把尺子，`--repeat 1`，切片 `0:50` / `50:101`）

| | killed/总 | 杀死率 | 存活 |
|---|---|---|---|
| 补测试前 | 58/101 | **57%** | 43 |
| 第一版（期望值取自字典） | 61/101 | 60% | 40 |
| **补测试后** | **98/101** | **97%** | **3** |

测试 **39 → 55 条**（参数化后 75 个用例）。补的东西按「它能怎么坏」分类：

| 补的是什么 | 坏起来长什么样 |
|---|---|
| 注册表十一行的 `counts` / `nightly`（19） | 一份归档悄悄不再被 I4/I5 看着，页面照旧印「OK」 |
| I4 回看窗口 `[-21:-1] if len>21 else [:-1]`（4） | 中位数算在错的窗口上，塌一半的那天不报 |
| `--repair` 的 `to_csv(index=False)`（1） | 修一次归档多一列无名索引列，**修两次多两列** |
| `keep_default_na=False`（1） | 一只真名叫 `NA` 的票和一只叫 `NULL` 的票都变成缺失值，I2 报一个不存在的重复，`--repair` 接着**删掉一行真数据** |
| I6a 的 `per.get(key, 0)`（2） | 某档面板页面上印 1、归档里 0 行，被读成「两边一致」 |
| `main()` 的 `return 0 if ok`（1） | **每一个干净的夜晚都 exit 1**，CI 天天拦着 commit |
| 四处报告初值 `rows: 0` / `drop_dupes: 0`（8） | 一份根本没写出来的归档报「1 行」；每份归档都像有个待修的重复 |
| I7 消息 `shells[:12]` / `> 12`（3） | 人读的那行少一个名字或凭空多一个省略号 |

⚠️ **I4 的窗口测不出来是因为中位数对单个离群值免疫**（09-02 已记过一次）。
一天的异常值移不动中位数，所以 fixture 造成**双峰**：十个 10 和十个 30，
窗口多一场少一场，中位数就在 20 和 10 之间跳，判决随之翻转。

## 五、剩下 3 个存活点，逐条判，两条实跑验过

| 存活点 | 判 | 证据 |
|---|---|---|
| L121 `len(per) > 21` → `>= 21` | **等价** | 两支只在 `len==21` 时分岔，而那时 `iloc[-21:-1]` 与 `iloc[:-1]` 都取索引 0..19。实跑 `len=1..40` 全部逐位相同，无一个长度分得开 |
| L139 `if key and rep["drop_dupes"]` → `or` | **等价** | `drop_dupes` 只在 `key` 非空时才被写（`audit_one`），所以 `key==[]` 与 `drop_dupes>0` 不能同时成立；另一侧（key 非空、0 个重复）`drop_duplicates` 是空操作。把两个版本的 `repair()` 在 6 种形状上都跑了一遍（干净 / 只有重复 / 只有坏日期 / 坏日期+重复 / 剔日期后剩重复 / 无 ticker 列），**返回值与写回文件逐字节相同** |
| L269 `json.dumps(indent=1)` → `2` | **化妆** | 只改 `--json` 落盘的缩进，`json.loads` 出来是同一个对象 |

⚠️ 前两条写的是「实跑六种形状都一致」，不是「已证明等价」——
枚举出来的一致是证据，不是证明。哪天 `audit_one` 改了 `drop_dupes` 的写入条件，L139 就该重判。
