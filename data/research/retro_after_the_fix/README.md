2026-09-01 我发现归档里有 **21 个 session 只扫了半个字母表**
（→ [`incidents/2026-09-01_half_the_alphabet_missing_for_six_weeks.md`](../../reference/incidents/2026-09-01_half_the_alphabet_missing_for_six_weeks.md)）。
查根因时发现一件比 bug 本身更值得说的事：

直到今晚才有人数它。

---

## 形状

**一个「从今天起不再发生」的补丁，不会自己告诉你「它已经发生了 N 天」。**

修复和回溯是两个动作，而我们只做第一个——因为第一个有明确的完成信号（测试变绿），
第二个没有任何东西提醒你去做。

## 这不是孤例

近三个月里，commit 标题明写「静默 / 从没 / 一直 / 没人发现」的修复，**17 条**：

| 有回溯（写清了吃掉多久 / 多少） | 没有回溯（只说「一直」「从没」） |
|---|---|
| `951e2e55` 静默跳过**五晚**，库从 **47%** 冻到 100% | `2c803bc3` 第二份「**一直**」在静默遮蔽第一份 |
| `894fccc2` **08-19 那一晚**的 breadth.json 缺四个字段 | `8b3805d7` regime score 接好了但「**从没**」被写出去 |
| `fcd3b133` 归档「silently capped at 5 rows」（记了，未量） | `4f223879` 三层「**再也不会**运行」 |
| | `2e9d3a25` 该字段「**从没**」进过 JSON |
| | `2f782b53` ← **本次事故的那一条** |

**做了回溯的那两条，都是当场就报了数字的**——说明这件事不难，只是没人要求。

## 提案（请 OPS 周检裁决）

**在 `CLAUDE.md` 的完成定义里加一句**：

> **修复一个「静默失效」时，交付物包含两样：补丁，和它已经吃掉多少历史的度量。**
> 答不出「它从哪天开始、影响了多少行/多少天」，这个修复只做了一半。
> 量不出来时，写明「量不出来，原因是 ___」——**这也是一个可接受的交付，
> 沉默不是。**

**为什么值得是机制而不是 memory**：这条的成本几乎为零（修的人此刻正好知道根因，
是全项目最容易算出这个数的时刻），而**放过它的成本是三周的脏数据没人知道**。
错过的窗口一旦关上，下一个发现它的人要从零重查一遍——我今晚花的正是这笔钱。

## 下轮第一件事（若 Andy 盲选未回）
