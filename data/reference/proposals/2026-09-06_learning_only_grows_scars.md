# 提案：这个体系只长疤，不长手艺

**给 OPS Fable。** Andy 2026-09-06 原话：「没有方法层，只有哪里是坑，记忆里只有哪里是坑但是没有方法，
这个是一个相对严重的问题。我们建立 skills 就是希望学习应该去这么做，不是什么做错了。
这件事情你汇报给 OPS，然后整个体系去想一下怎么样去进化。」

提出人：前端线（Rotation）。**本文是提案，不是规矩**；除了下面第五节已执行的两项，其余等 OPS 盘完、Andy 裁。

## 一、先看数

| | 数量 |
|---|---|
| 共享记忆总条数 | 192 |
| 其中 `pitfall_*`（哪里是坑） | **66** |
| 其中方法类（怎么做对） | **0**（09-06 之前） |
| `KNOWLEDGE.md` 的层 | 权威 · 结论 · 教训 · 台账 · 资料——**没有方法层** |
| 收工三问里问「做成了什么」的 | **0 问**（三问全在问事故） |

三次律有两款：①同类活**成功**干到第 3 次＝写成 SOP/skill，登记进 `KNOWLEDGE.md`；
②同形状的**坑**踩到第 3 次＝升级为机制。**②反复生效，①一次都没生效过。**

## 二、为什么只有一款在跑（这是机制问题，不是态度问题）

**1. 计数器没有输入。** ①要求数到 3。但第 1 次和第 2 次成功从来没有被记录到任何地方，
所以永远数不到 3——**规则要求统计一种它自己没安排任何人记录的事件**。②能跑，正因为坑账
把第 1、2 次都写下来了，第 3 次一比对就认得出。这是全部原因里最硬的一条。

**2. 坑会自己敲门，方法不会。** 出事有中断信号：报错、Andy 皱眉、页面白了。做对了没有信号，
它安静地过去。事件驱动的规则能跑，需要「注意到缺席」的规则跑不动——没人会注意到缺席。

**3. 方法没有落脚点。** 记忆的类型只有 user / feedback / project / reference 四种；
`KNOWLEDGE.md` 五层没有方法层。一样东西没有地址，就不会被写下来。

**4. 终态选错了。** 就算写下来，写成 memory 也是**被动**的：要有人在开工时想起来去翻索引。
Andy 那句「我们建立 skills 就是希望学习应该去这么做」点的正是这个——**skill 按 description 自动触发，
memory 要靠记性**。方法的终态应该是 skill，memory 只是它的草稿箱。

## 三、提案（请 OPS 逐条裁）

**P1 · 把触发点从「第 3 次成功」改成「被接受的那一刻」。**
可靠的、可检测的事件不是重复三次，是 **Andy 在纠正 N 轮之后说了「都批」「OK」「y，合」**。
那是一个和报错一样明确的中断。凡是「改了 ≥3 轮后被接受」的产出，收工时必须把方法写下来。
——不用再数到 3，因为接受本身就是判据。

**P2 · 给成功一个记账面。** 与坑账对称的方法账（`memory/method_*` + `MEMORY.md` 的 Methods 节，
09-06 已建）。**append-only，各线可写。** 有了它，①的计数器才第一次有输入。

**P3 · 方法的晋升路径写死：`method_*` 记忆 →（同一条被三条线引用过 / 或连续两周被引用）→ skill。**
skill 才是终态。晋升由 OPS 周检执行，不靠产出者自觉。

**P4 · 回溯开采。** 过去几个月的已接受产出里埋着大量没被写下来的方法（课程、周信、拆解、
数据管线、页面改版都各自有一套已经被 Andy 裁过的标准动作）。这是同构批量任务、量 >10，
按宪法该用 Workflow fan-out 开采一次，产出直接进方法账。**这一项要花钱，请 Andy 单独点头。**

**P5 · 体检指标。** 周检报一个数：**本周新增 方法条数 : 坑条数**。
长期只有坑没有方法，说明体系在结疤不在长本事。这个数比任何自述都诚实。

**P6 · 收工三问的①已改（见下）。** 请 OPS 检查各线任务书里是否还有只问事故的收工模板，一并对齐。

## 四、一条要提防的反作用

方法账会诱发**为了记而记**——把每件小事都写成"标准动作"，一年后是 200 条没人读的方法，
比 0 条更糟。护栏建议写进 P2：**方法必须来自被接受的真实产出**（引得出是哪一轮、谁裁的），
**不许从设想里写方法**。坑账当年也是靠这条活下来的：每条坑都指得出那个 commit。
