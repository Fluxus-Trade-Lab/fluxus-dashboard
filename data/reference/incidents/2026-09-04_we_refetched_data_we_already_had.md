# 我们重抓了两遍已经抓到的数据

**2026-09-03/04 · dashboard 停更两天 · 归 OPS + DATA ALEX**

## 一句话

那两天的数据，我们成功抓到过两次，两次都被自己的闸扔了；然后我们用「重抓」去修闸的问题，
五次全量重拉把 runner 的机房 IP 从 429 打到 `HTTP 401 Invalid Crumb`。
**上游是被我们打坏的，不是先坏的。**

## 根因

不是「Yahoo 限流」。三层：

1. **闸红＝数据蒸发。** 工作流没有任何 `upload-artifact`；闸拒发布，`data/output/` 随 ephemeral runner 一起没了。
   「不发布坏数据」被实现成了「不保留任何数据」——**这是两件事**。
2. **两种失败在日志里长得一样。** `Process completed with exit code 1` 既是「上游拒绝我们」也是「我们拒绝自己」，
   而这两种的正确下一步是**相反的**：前者要等，后者绝不能重抓。没有工具区分，就只能靠肉眼，肉眼当晚判错了。
3. **任务书把错的那条写成了规矩。** 哨兵的原文：「C 数据完整性违规：main 已有对应修复 commit → **可重跑**」。
   它照做了。ABSI 的修复 `d6fec77e` 确实在 main 上，于是它一小时一发，发了五发。

第 3 层最值得记：**这不是它判断失误，是我们给了它一条会自伤的指令。**

## 验证（Andy 的原话：「然后验证」）

分诊器的考卷就是这场事故本身：九条真实账本记录固化在
`pipeline/tests/fixtures/run_ledger_2026-09-03.jsonl`，测试断言 **23:29 和 02:31 必须判 `C_gate`、
且下一步必须包含「不要重抓」**。注入「一律判成上游问题」这个真 bug 时，14 条里红 5 条。

回放时还撞出一个陷阱并当场修掉：**成功的班次抓取质量最好，不给「这一班失败了」这个前提，
它会被判成「闸拒了好数据」**——06:12 那班就被误判过一次。所以 `failed` 进了函数签名，
不留在文档里等人记得。

## 三次律盘点

同形状的坑第几次：

- 「闸对、测试对、**没人调用**」——这次是反过来的第二次：接线在，但接的是一条**错的**指令。
  上次（`pitfall_tested_the_module_not_the_wiring`）是模块没被调用；这次是模块被调用了，
  调用它的那句话本身是自伤的。**下次审任务书要问的不是「这条被执行了吗」，而是「执行它会发生什么」。**
- 「诊断不是修复」——第 3 次。这次没重犯：分诊器合进 main 的同一小时里，任务书也改了。
