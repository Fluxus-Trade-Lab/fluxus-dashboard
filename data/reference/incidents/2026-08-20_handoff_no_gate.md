## 三、根因链（五个为什么）

1. 意见没送到 → 收信会话已结束。
2. 为什么结束就丢 → **消息信道的寿命等于进程寿命**，而工作的寿命是仓库的寿命。
3. 为什么没走耐久信道 → `DATA_CONTRACTS` §七 就是为此设的（标题原话「跨会话消息会丢」），但**它是靠自觉，没有闸**。
4. 为什么没人发现 → 没有任何东西在检查「有活儿committed 了却没 push」。归档有 I1–I6 每晚重读，交接一条都没有。
5. 为什么这类事故反复 → **数据层的可靠性做完了，协作层还停在"约定"阶段**：约定写在文档里，没有可机器判的不变量。

## 四、这不是孤例

§七 的标题自己写着「跨会话消息会丢，2026-08-17 就丢过一封」。08-17 丢了一封，立了规矩；08-20 又丢一封，**规矩存在但没人用**。一条只靠记性执行的规矩，第二次就失效了。

同一次核对里还暴露第二种同型问题：前端在 08-21 三次引用「tickers 空壳 92/185」，实际当时是 11/188 —— 断言的是现状，依据的是昨天的测量。**空壳数是个会自己波动的量**（每晚 cron 会补回来），拿它当损害规模，等于给自己一个「今天好像没那么糟」的假信号。真正不变的是机制：`write_ticker_json()` 无条件覆盖。

**H3 的两个设计坑（第一版都踩了，写下来免得重犯）：**

1. **年龄量在 tip，不是量在最老的 commit。** 问的是「这份没发布的活儿多久没人碰了」；量最老的 commit 回答的是另一个问题——从未 push 的基座分出去的分支，不管多活跃都永远显示"最大程度搁浅"。第一版就这样，把唯一一条真发现埋在 17 个共享同一个 167 天老基座的 ref 底下。
2. **搁浅要和废弃分开。** stranded = 停在 `--hours`（默认 12h）与 `--stale-days`（默认 14d）之间；abandoned = 更老的，是考古不是交接事故，只计数、`--all` 才列。首跑 22 个 ref 未 push，分桶后 **6 搁浅 / 16 废弃**——**每晚响 22 次的警报，和从不响的警报，被读的次数一样多**。这跟上面那个「92」是同一种病：让一个不可行动的数字冒充损害规模。

只能在本机跑：GitHub cron 是全新 clone，永远看不见这台 Mac 的工作树。

## 六、行为规则

1. **跨会话的请求和答复，先往 `DATA_CONTRACTS` §七/§八 写一行，再发消息。** 消息是通知，契约行才是投递。
2. **手上有未 push 的 commit 就别结束会话。**
3. 收到发错的群发消息：核实是不是自己的；不是也要**先把它记进耐久处**再告诉人，别只回一句「不是我」。
4. 引用数字前先重测。**断言现状就得用现状的测量**；引用昨天的数就说明是昨天的。
5. 报损害挑**不会自己波动**的量——机制、根因、被覆盖的次数，而不是当日存量。
