## ⚠️ 09-01 的病因判定是错的，今天纠正

09-01 我写「**断在 `git worktree add` 那一步**」。今天的逐条 trace 否掉了这个判定：

```
20:36:13 TOOL  git fetch + ls-tree campaigns      → 20:36:20 有结果
20:36:13 TOOL  git show BRAIN.md                  → 20:36:20 有结果
20:36:23 TOOL  git show RECORD.md                 → 20:36:23 有结果
20:36:25 TOOL  git show INBOX.md                  → 20:36:25 有结果
20:36:36 TOOL  git worktree add --detach          → 【无结果】
20:36:37 TOOL  git show 06_gate_review.md         → 【无结果】
```

**它发出了 worktree add 之后又发出了下一条读取命令**——说明它没有卡在那一步、也没有报错。
最后两条**都没有回结果**：进程是在第 33 秒被整体切断的，不是某条命令失败。
**没有任何错误信息，因为根本没有失败——只有截断。**

这条更正本身值得记：**「最后一条命令」不等于「失败的那条命令」。**
一个被截断的 trace，末尾长得和一个崩在末尾的 trace 一模一样；
区分它们的唯一判据是**倒数第二条有没有回结果**。

## 为什么 09-02 新加的补丁没救回来

产线 SKILL.md 09-02 新加了 `⛔ 第 −1 步：本次运行必须留痕`——
「**本次运行无论结果如何，收工前必须往 INBOX 追一行**」。老板每日页把它写成「今晚 05:35 首测」。

**首测没过，而且它按设计就过不了**：那条指令挂在**收工**位置，
而这个班从来活不到收工。**给一个在第 33 秒被杀死的进程加一条收尾义务，是没有效果的。**

## 建议的机制（我不动手：SKILL.md 是定时任务且归 Steve 线，须走 `update_scheduled_task`，禁 Write/Edit）

把留痕从**收工**挪到**开工**：该班的**第一条**动作就是往 INBOX 追一行起跑占位
（Zac 04:35 落「晨报骨架」就是这个做法，他那条从没丢过班）。
实测支持这个位置可行：33 秒内它完成了 4 次带结果的 `git` 调用，**足够一次 append + push**。

⚠️ 但占位行只解决**可观测性**，不解决**为什么 30 秒就被杀**。两件事分开办：
1. **可观测性**（Steve 线，今晚可落）：开工即留痕。
2. **存活**（需要 Andy 或 OPS 看 harness 侧）：连续三班都在 23–33 秒被切断，
   且三次都发生在 05:35–05:36 这个窗口，**不像任务书的问题，像这个班的运行环境的问题**。
   参照组：同夜 `zac-night-study`（04:32 开工）跑满四个多小时、落 20+ commit，同一台机器同一个仓库。
